# 判决(2026-08-18,跑批后写入)

## 猜想被否定,且方向与预期相反:QVF_DATE_STRICT 在 S5 上是灾难性的

判据③触发(≤ −3.0pp):**该修复有害,不得默认开启。**

| 主判据:183 题(证据包被改变者) | |
|---|---|
| DATE_STRICT 关(归档) | **88.52%**(162/183) |
| DATE_STRICT 开 | **13.11%**(24/183) |
| **Δ** | **−75.41pp** |
| McNemar | 关对/开错 b=**143**,关错/开对 c=**5**,χ²=126.82,**p<0.001** |

**四个题型无一幸免**:first_vs_last −89.13 / longest_tenure −77.78 /
change_count −73.91 / count_before −60.87。

拼回全量 418(235 题证据未变、沿用归档):**83.73% → 50.72%,−33.01pp**。

## 根因:规范化过度,不是相对时间解析误判

预注册要求区分二者。查实是前者,且可定位到一行行为:

```
qvf.datenorm.normalize('2011-00-00') -> (None, 'reject_out_of_range')
qvf.datenorm.normalize('2011-03-00') -> (None, 'reject_out_of_range')
```

S5 的题面用 `YYYY-00-00` 编码**年粒度的 "Today"**(如
`(Today is 2011-00-00.) Which employer did I hold the longest?`)。
`datenorm` 把月/日为 `00` 判为越界并整个拒绝 → 题面日期不可解析 →
WINDOW/ASOF 过滤清空 → 证据包归零 → 读者回答"我没有你的雇佣记录"。

证据链:
- `evidence_n` 均值 **3.83 → 1.69**;**证据完全为空的题 0 → 52**
- `compile_ok` 183 → 183 **不变**(不是编译失败,是执行期证据被清空)
- 处理组 183 题中含部分日期的占 **56.8%**,而未受影响的 235 题只占 **12.8%**

## 这个缺陷为什么此前没被发现

`qvf/datenorm.py` 模块头写明:诊断在 30 个卡片库、40,088 条带日期记录、
10,422 种日期串上复算,证明"只要输入合规,现行字符串比较就是正确的"。

**但那 10,422 种串全部来自卡片侧**——WikiState 由 Wikidata 限定符生成,
产出干净的 `YYYY-MM-DD`(本次抽 40 个 uid 的 297 条 `stated_date`,**297/297 完整**)。
**题面侧的日期从未进入该验证集**,而年粒度的 `YYYY-00-00` 只出现在题面。

模块自己的话是"真实世界优先(而非数据集优先)",而它恰好在这一点上
只看了数据集的一半。

## 结论与下一步(不是"别开这个旗标")
1. **默认保持关闭。** 现状即安全。
2. 正确的修法是让 `normalize` 把 `YYYY-00-00` / `YYYY-MM-00` 当作
   **年/月粒度的合法日期**,而非越界拒绝。
3. 但改完**不能只补这一处**:模块的安全性论证是"下游字符串比较在合规输入上
   正确",而一旦产出 `YYYY` / `YYYY-MM` 这类新粒度串,
   混粒度的字符串序**不再保序**(实测 `'2011' < '2011-03-01'` 为真,
   `'2011' < '2010-12-31'` 为假)。**补粒度必须同时改下游比较,否则换一种崩法。**
4. 重测须同题重跑本 183 题子集(约 $1)。
