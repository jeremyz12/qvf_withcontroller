## 主要发现 ①:usability 的收益在计数题上是**结构性编码**,"教会优于接管"措辞过强

`change_count`(105 题)上:

| | |
|---|---|
| 标注 usable 行数−1 恰好 == gold 的题 | 77/105 |
| usability 臂答对的题 | 76,**全部落在这 77 题内** |
| 标注行数 ≠ gold 的 28 题 | **0 对** |

条件准确率 **98.7% vs 0%** 的锐利二分:读者做的是**数被认证过的行数**,
不是"学会判断可用性"。`count_before` 同型:结构编码率 83.8%,臂成绩恰为 83.81%。

**这不推翻 +11.24pp(选出正确记录集正是机制主张),但推翻其解释**:
标注的价值是**认证证据集的完整性与角色**("此列表即全集,一行一态"),
而非教会读者判断。论文措辞必须从「教会」改为「证据集认证」,
否则审稿人做同样的行数统计就能拆掉这个词。

## 主要发现 ②:token 预算匹配只匹配了**读取侧**,全口径下基线只拿到 22% 预算

executor 的 2,069 tok/题不含建卡。S5 的 105 个 uid 在 v42 上的建卡实测
**in 2,279,776 / out 772,858**,摊到 418 题 = **7,303 tok/题**,
全口径 = **9,372 tok/题**。A 臂(2,097)只有它的 **22%**,B 臂(3,443)37%。

本项目此前自己用过含摊销记法(HANDOFF §七 "1,724+767"),本实验未沿用,
**且预注册没有声明口径选择** —— 这是口径漏洞,不是笔误。

缓解因素:预算曲线平坦(每翻倍 +2–3pp),外推到 9.7× 也难及 83.73%。
**但这是外推。判据"主张成立"应降格为"读取侧口径下成立"。**
补法:跑 `full_context_direct`(整库入上下文,run_decisive_stale 已有该条件),
它是天然的全口径基线,S5 上预估 ≈$3–5。**跑完之前,"预算不能解释机制差"
不得以全口径口吻出现在论文里。**

## 主要发现 ③(设计,须在花钱前改):实验 C 的 dim2 两侧问法不匹配

预注册 C 表承诺替换侧问"我换过几次手机"对应集合侧"我有几个爱好"。
**但 `gen_stale_chain.py` 没有任何计数问法**(dim2 是预设陷阱题,gold=末值),
而 `gen_setchain.py` 的 dim2 是计数题(gold=len)。
两批的 dim2 比较将把「问法类型差异」混进唯一自变量,**C 的 dim2 格作废**。

修法二选一(须在跑臂前定):
a) 补造替换型孪生批:同 seed 日期、同模型、加 `q_count`("换过几次"),≈$6;
b) 预注册限定比较只用 dim1/dim4/dim5,弃 dim2。
**推荐 a**——计数恰是 set/replacement 语义分歧最大的问法,弃掉可惜。
