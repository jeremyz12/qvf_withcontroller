# 写入侧闭集拆除 · 设计稿(2026-08-16)

> 状态:**设计,未实现**。依赖正在跑的"顺序不变抽取"(QVF_WRITE_PERSESSION)的装配层落地后接入。
> 定位:去耦合路线图原则 2("闭集→开放+规范化")的写入侧一半;读取侧一半已于 08-16 由 QVF_OPEN_SLOT 完成(闭集外域 21.3%→60.0%)。

## 一、问题(全部有实测)

**现状**:建卡契约 Rule 7 规定 `slot_class` 必须是七类闭集之一,或 `other:<short-noun>` 逃逸。

**实测缺陷**:
1. **过半状态落在闭集外**。样本库 wikiP108011:44 张卡分成 16 个键,其中 **23/44 = 52% 的卡片 `slot_class` 是 `other:*`**(other:hobby / other:plants / other:education / other:healthcare / other:service / other:subscription / other:achievement / other:business)。
2. **`other:*` 是下游二等公民**。SLOT_ALIASES 只列七个具名类;`_keyed_depth` 对无类命中返回 `None` → 路由拿不到键控深度信号 → 被派去 prompt/direct 臂。路由日志中 `keyed_depth=0/None` 的题确实全部分派到 prompt/direct。
3. **跨域实测代价**:零改动新域测试中,P69 就读学校落入 `other:education`,键控路径整体失效,**闭集内 78.7% vs 闭集外 21.3%,差 57.4pp**,触发预注册判据(a),"键控机制可泛化"**已正式撤回**。
4. **用户场景直击**:"上一个 query 问职业,下一个问饮食"——职业在闭集内(全功能),饮食落 `other:diet`(降级)。**话题切换本身零成本(系统按题无状态),但质量随话题在闭集内外跳变。**

## 二、设计:闭集 → 开放词表 + 装配时规范化

**关键认识:不能只是"删掉闭集"。**闭集现在承担着**规范化**职责——把模型自由写的 `slot`("plants_owned"/"phone_case"/"food_delivery_app_used")收敛成可分组的键。直接开放会导致**同义分裂**:"phone" / "mobile" / "cell phone" 变成三个键,链被切碎,深度被低估,路由反而更差。

**因此改法是"替换"而非"删除"**,三层:

### 层 1 · 抽取:`slot_class` 改为开放字符串
- Rule 7 从"EXACTLY one of 七类|other:<noun>"改为"a short canonical noun phrase naming the attribute";
- 同时**要求 `slot_cardinality` 明确给出 `single`/`set`**(该字段 schema 早已存在,但读取侧从不消费——见 08-16 讲解发现;顺序不变抽取那一轮已要求填准);
- 其余规则(逐字锚点契约等)逐字不动。

### 层 2 · 装配:store 内槽位规范化(这是新增的核心机制)
在**单个库内**把自由槽位名收敛成规范键:
- **字符串归一**:小写、去下划线/连字符、去 `other:` 前缀、词干化;
- **嵌入聚类 + merge-or-attach 不变量**:直接复用 P2 已实现的 `build_tag_lattice.py` 机制——新槽位名必须与库内既有键**合并**(相似度 ≥τ 且模型复核同义)或**挂为其子类**,**禁止孤立节点**;
- **符号层否决权**:沿用 08-16 开放槽位修复的教训——嵌入命中必须能被规则否决(那一轮 dev 轮 1 的覆盖式嵌入产生过 `employer→other:habit` 余弦 0.499 的垃圾救援);
- 产出 `canonical_slot` 字段,**保留原始 `slot` 与 `slot_class` 不删**(可回溯、可消融)。

### 层 3 · 读取:键控改用 `canonical_slot`
- `_keyed_depth` 与 `_store_max_depth` 的分组键从 `slot_class`(闭集)改为 `canonical_slot`(开放);
- 问题侧槽位短语→ `canonical_slot` 的匹配复用已上线的 `QVF_OPEN_SLOT` 通路(字符串归一 + 嵌入 + 词表否决权);
- **全部走新旗标 `QVF_OPEN_SLOTCLASS=1`,默认 0,旗标关时逐字节不变。**

## 三、三个难点与对策

| 难点 | 为什么危险 | 对策 | 怎么验 |
|---|---|---|---|
| **同义分裂** | 开放词表后键数暴涨、链被切碎、深度低估 → 路由退化到比现在更差 | 层 2 的 merge-or-attach 不变量;**τ 在 dev 上校准**(精确率约束下最大化召回) | **判据②:键数不得显著增加、平均键控深度不得显著下降**(对同一库前后对比) |
| **过度合并** | τ 太松会把 `employer` 和 `other:business` 并成一个键,链被污染 | 符号层否决权(词表命中即否决嵌入救援);**property 类边需蕴含复核**(P2 已实现,该轮拒掉 11 条幻觉边) | 消融:关掉否决权 / 关掉蕴含复核,各自的键纯度塌陷幅度 |
| **历史教训:矫枉过正** | 严格覆盖规则迭代 3 因范围限定过头崩了覆盖(P39ext 154→105),按纪律被三表否决封笔 | **主指标用精确匹配率**(天然两侧都罚),另报值级 P/R 作诊断;dev ≤3 轮封笔 | 判据①(下) |

## 四、预注册判据(实现前定稿,不得挪动)

- **① 主判据(质量)**:同一 50-uid 子集上,新路径的**卡片链 vs 源链精确匹配率**不低于 B6 基线区间下界 **52.1%**,且点估计**不显著低于 70.0%**;若同时跑 ≥2 轮,**方差应不高于 B6 的 ±20pp**。
- **② 结构护栏(防同义分裂)**:同一库内,**规范化后的键数 ≤ 闭集下键数 × 1.3**,且**平均键控深度 ≥ 闭集下 × 0.9**。破线即弃刀。
- **③ 泛化主判据**:在新域测试的 **P69(就读学校,闭集外)** 上重跑 S1-S4 与 S5,**键控深度不再为 0/None**,且成绩**不低于修复后的 60.0%**;闭集内 **P26** 作阳性对照,**不得回退超过 1pp**。
- **④ 冻结不变**:旗标关时 `_catalog_prompt()` 与读取路径逐字节不变(对拍验证)。

## 五、与"顺序不变抽取"的关系:共用装配层

正在跑的 `QVF_WRITE_PERSESSION` 已经把建卡拆成"抽取层(LLM)+ 装配层(纯代码)",而装配层**本来就要做槽位名归一**(因为逐会话抽取失去了原 Rule 2 的"consistent slot names across records"全局约束)。

**所以本设计的层 2 应当直接实现在那个装配层里,而不是另起炉灶。**两件事天然复合:
- 顺序不变抽取解决**同一内容不同顺序产出不同标签**;
- 闭集拆除解决**标签词表被人为限死在七类**。
共同的落点都是"装配时把自由槽位名收敛成稳定的规范键"。

**排期**:等顺序不变抽取出判决 → 若其装配层可用,本设计接在其上;若被否,本设计需自带装配层。

---

## 六、为什么这次可能成(而 P2 那次失败了)

P2 的开放标签本体归纳主判据被否定(召回 4.5% vs 门槛 60%),根因是**生产格只从 30 个 dev-uid 归纳,与 28 个 test-uid 的标签词表几乎不交集**,格闭包在 test 上几乎从未触发。

**但槽位规范化是 store 内问题,不需要跨用户迁移。**"这个库里 `phone` 和 `mobile` 是同一件事"只依赖这个库自己的槽位名集合;它不需要从别的用户那里学到什么。P2 失败的那个结构性障碍(跨 uid 词表不交集)**在这里不存在**。

这也印证了 P2 留下的那条设计洞察:"从观测标签归纳私有格,是私有本体与共享世界知识两种部署形态之间最差的一种。"——槽位规范化恰好是**纯私有**的那一端,是这套机制该用的地方。
